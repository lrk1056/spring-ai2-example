1. 什么是 AI Agent？它与普通的 LLM 对话应用有什么本质区别？

答案： AI Agent（智能体）是以 LLM 为"大脑"，能够自主感知环境、规划任务、调用工具、执行行动并根据反馈迭代，最终完成复杂目标的系统。

与普通对话应用的本质区别：

- 被动 vs 主动：普通 Chatbot 是一问一答的被动响应；Agent 会自主拆解任务、决定下一步动作，可能一次任务中执行多轮 LLM 调用。

- 是否使用工具：Chatbot 只能靠模型参数知识回答；Agent 能调用外部工具（搜索、数据库、代码执行、API）获取实时信息或改变外部世界。

- 是否有循环：Agent 的核心是"感知 → 规划 → 行动 → 观察"的循环（Acting Loop），直到目标完成。

- 记忆与状态：Agent 通常具备短期记忆（对话上下文）和长期记忆（向量库存储），能从历史交互中积累经验。

一个经典公式：Agent = LLM（推理） + 规划（Planning） + 记忆（Memory） + 工具（Tools）


2. Agent 的核心架构组成有哪些？

答案：

- 规划（Planning）：

  - 任务分解：Chain of Thought（思维链）、ReAct、Plan-and-Execute，把大目标拆成可执行的子步骤。

  - 反思（Reflection）：对执行结果自我评估并修正，如 Reflexion 模式。

- 记忆（Memory）：

  - 短期记忆：上下文窗口内的对话历史。

  - 长期记忆：外部向量数据库（检索历史结论、用户偏好），通过 Embedding 检索。

- 工具使用（Tool Use）：Function Calling / Tool Calling，让模型选择并调用外部 API；MCP（Model Context Protocol）标准化工具接入。

- 行动（Action）：执行工具调用的运行时环境（沙箱、代码解释器等）。


3. 什么是 ReAct 模式？它的工作原理是什么？

答案： ReAct = Reasoning + Acting（Yao et al., 2022），是最经典的 Agent 执行范式。

工作原理是一个交替循环，每轮产生三个部分：

- Thought（思考）：模型分析当前状态，推理下一步该做什么。

- Action（行动）：决定调用哪个工具及参数。

- Observation（观察）：接收工具执行结果，作为下一轮思考的输入。

Question: 北京今天多少度，适合穿什么？
Thought: 我需要先查询北京当前天气
Action: get_weather(city="北京")
Observation: 晴, -2°C, 风力3级
Thought: 天气寒冷，我可以给出穿衣建议了
Answer: 北京今天晴，气温-2°C，建议穿羽绒服、戴帽子手套...

优势：将推理与行动交织，模型的推理可以基于真实工具结果而非臆想，显著降低幻觉。

在 Spring AI 中，工具调用的多轮编排由框架自动完成（内部实现即 ReAct 风格的循环），开发者注册 @Tool 即可。


4. 什么是 Function Calling / Tool Calling？它的完整执行流程是怎样的？

答案： Function Calling 让 LLM 能"请求"应用程序执行预定义函数，是 Agent 与外部世界交互的桥梁。

完整流程：

- 注册工具：应用向模型提供工具列表（名称、描述、JSON Schema 参数定义）。

- 模型决策：用户提问后，模型判断是否需要调用工具，若需要则输出结构化的 tool_calls（函数名 + JSON 参数），模型本身不执行函数。

- 应用执行：应用解析 tool_calls，在本地（或远程）执行真实函数。

- 结果回传：将执行结果作为 tool 角色消息返回给模型。

- 继续推理：模型结合工具结果继续生成——可能再次调用工具（循环），也可能给出最终答案。

关键理解：LLM 负责"决定调用什么、参数是什么"，应用负责"真正执行"，二者通过 JSON Schema 约束的协议协作。Spring AI 用 @Tool 注解声明，框架自动完成 schema 生成与结果回传循环。


5. 什么是 MCP（Model Context Protocol）？它解决了什么问题？

答案： MCP（模型上下文协议）是 Anthropic 于 2024 年底开源的标准化协议，用于规范 AI 应用与外部数据源/工具之间的连接方式，被称为"AI 界的 USB-C 接口"。

解决的问题：

- M×N 集成困境：M 个 AI 应用要对接 N 个工具/数据源，原本需要 M×N 种定制集成；MCP 将其变为 M+N——工具方实现一次 MCP Server，所有支持 MCP 的应用都能使用。

- 生态复用：文件系统、数据库、Git、浏览器等已有大量现成 MCP Server 可直接复用。

核心概念：

- MCP Host：运行 AI 应用的宿主（如 Claude Desktop、IDE）。

- MCP Client：宿主内与 Server 保持 1:1 连接的客户端。

- MCP Server：对外提供三类能力——Tools（可执行的工具）、Resources（可读取的资源）、Prompts（提示模板）。

- 传输层：stdio（本地进程）、SSE / Streamable HTTP（远程服务）。


6. 什么是 RAG Agent？RAG 与 Agent 如何结合？

答案： RAG Agent 是将检索增强生成嵌入 Agent 决策循环的智能体——不再"固定先检索再生成"，而是让模型自主决定何时检索、检索什么、是否需要再检索。

结合方式：

- 作为工具：把向量库检索封装成一个 Tool（如 search_knowledge_base(query)），Agent 在推理中按需调用；复杂问题可拆解出多个子查询分别检索。

- 自适应检索：模型先判断"我是否知道答案"（Self-RAG 思想），不知道才检索，降低无谓开销。

- 迭代检索：第一轮检索结果不满意时，Agent 可改写查询（query rewrite）再检索，或结合反思机制补充检索。

- 多路融合：Agent 可同时调用多个检索工具（向量库、Web 搜索、SQL 查询）并对结果做对比综合。

Spring AI 实践：将 QuestionAnswerAdvisor 用于简单固定 RAG；将向量检索封装为 @Tool 注册给 ChatClient，即可实现"Agent 自主决定检索时机"的 RAG Agent。


7. 什么是多 Agent 系统（Multi-Agent）？常见的协作模式有哪些？

答案： 多 Agent 系统让多个各司其职的 Agent 通过协作完成单个 Agent 难以胜任的复杂任务，类似人类团队的分工协作。

常见协作模式：

- 主管模式（Supervisor / Orchestrator-Worker）：一个主 Agent 负责任务拆解与分派，子 Agent 执行后汇报，主 Agent 汇总（如 Claude Code 的 subagent 机制、LangGraph 的 Supervisor 架构）。

- 流水线模式（Sequential / Pipeline）：Agent 按顺序传递产物，如"需求分析 → 编码 → 测试 → 文档"。

- 辩论/评审模式（Debate / Review）：多个 Agent 独立给出方案，互相评审批判，取最优（如生成-评审分离）。

- 群聊模式（Group Chat）：多 Agent 在共享上下文中自由发言，由管理 Agent 决定下一个发言者（AutoGen 风格）。

- 分层模式（Hierarchical）：Agent 组织成树状结构，逐层拆解执行。

关键挑战：通信协议设计、上下文共享方式（传全文还是传摘要）、冲突解决、成本控制（Agent 数量 × 轮次的 Token 放大效应）。


8. Agent 开发中的主要挑战有哪些？如何缓解？

答案：

- 幻觉与错误行动：模型可能调用错误的工具或编造参数。缓解：工具描述清晰精确、参数 JSON Schema 校验、执行前确认（human-in-the-loop）、限制可用工具集。

- 错误累积/雪崩：多步任务中前面的小错误被后续步骤放大。缓解：每步结果校验、反思机制、检查点回滚。

- 上下文窗口限制：长任务历史迅速撑爆窗口。缓解：记忆压缩/摘要、外部长期记忆（向量库）、只传递必要状态。

- 无限循环与失控成本：Agent 反复尝试同一失败操作。缓解：设置最大迭代次数、超时、循环检测、Token/预算上限。

- 安全性：提示注入（Prompt Injection）可能通过检索到的恶意文档或工具返回值操纵 Agent。缓解：输入消毒、权限最小化、沙箱执行、敏感操作二次确认。

- 可观测性差：多轮调用链路复杂难排查。缓解：全链路 trace 记录（每步 Thought/Action/Observation 落日志）、Langfuse/OpenTelemetry 等观测平台。


9. 什么是 Agentic RAG 与 Agentic Coding？举例说明典型应用。

答案：

- Agentic RAG：以 Agent 方式实现检索增强——模型自主决定是否检索、检索哪个源、检索几次，并能对检索结果做评估和二次检索。区别于传统"一次检索、固定流程"的朴素 RAG。

- Agentic Coding：Agent 自主完成编程任务——理解需求、浏览代码库、编写修改代码、运行测试、根据失败信息自我修复，循环直到任务完成。典型如 Claude Code、Cursor Agent、Devin。

Spring AI 生态中的对应实践：

- 用 @Tool 封装检索器、数据库查询、业务 API，交给 ChatClient 编排。

- 用 Advisor 机制注入记忆与 RAG 能力。

- 配合 MCP 接入海量现成工具生态。


10. 如果让你用 Spring AI 设计一个"面试题问答 Agent"，你会怎么设计？

答案（开放题，参考要点）：

- 工具层：

  - search_knowledge_base：向量库检索面试题文档（RAG）。

  - save_question：将用户收藏的题目写入数据库。

  - get_random_question：按主题随机出题。

- 记忆层：MessageWindowChatMemory 维护多轮对话；记录用户薄弱知识点作为长期记忆（存向量库）。

- Advisor 层：MessageChatMemoryAdvisor（会话记忆）+ SimpleLoggerAdvisor（日志）。

- System Prompt 设计：明确角色（面试官）、行为准则（先检索再回答、难度递进、回答后追问）。

- 流式与隔离：stream() + SSE 输出；conversationId 区分不同用户会话。

- 护栏：限制工具调用次数、敏感问题拒答、输出长度约束。

ChatClient interviewer = builder
    .defaultSystem("你是资深Java面试官，回答前先用工具检索知识库，基于检索内容作答")
    .defaultTools(new KnowledgeBaseTools(vectorStore), new QuestionTools(repo))
    .defaultAdvisors(MessageChatMemoryAdvisor.builder(chatMemory).build())
    .build();

该题考察点：是否理解 Agent = 工具 + 记忆 + 规划 + 循环，能否落到 Spring AI 的具体组件上。
